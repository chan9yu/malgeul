# SPEC

각 기능이 정확히 어떻게 동작하는지 정한다. 누구의 어떤 문제를 왜 푸는지는 `product/PRD.md`에, 각 화면에 무엇이 놓이는지는 `design/DESIGN-SPEC.md`에 있다. 기술 결정 기록은 이 문서의 마지막 절이다.

## 동작 규칙

### 업로드 검증

파일을 받으면 아래 순서로 검사한다. 처음 걸린 항목 하나의 이유만 보여주고 거절한다. 거절해도 업로드 영역은 기본 상태로 돌아가 다른 파일을 바로 받을 수 있다.

1. 개수: 한 번에 한 파일만 받는다. 두 개 이상을 끌어다 놓으면 거절한다
2. 확장자: 파일 이름이 `.mp4`나 `.mov`로 끝나야 한다. 대소문자는 가리지 않는다
3. 크기: 2GB(2,147,483,648바이트)를 넘으면 거절한다
4. 길이: 영상 메타데이터에서 재생 시간을 읽어 2시간(7,200초)을 넘으면 거절한다. 메타데이터를 읽지 못하는 파일도 여기서 거절한다

거절 문구는 걸린 이유를 그대로 말한다.

| 걸린 검사  | 문구                                                       |
| ---------- | ---------------------------------------------------------- |
| 개수       | 파일은 한 번에 하나만 받습니다                             |
| 확장자     | mp4나 mov 파일만 받습니다                                  |
| 크기       | 2GB를 넘는 파일은 받을 수 없습니다                         |
| 길이       | 2시간을 넘는 영상은 받을 수 없습니다                       |
| 메타데이터 | 영상 정보를 읽지 못했습니다. 파일이 손상되었을 수 있습니다 |

검사를 모두 통과하면 변환 확인 화면으로 넘어가 파일 이름과 크기, 재생 시간을 보여준다. 변환은 사용자가 "변환 시작"을 눌러야 시작한다.

크기 표기는 이진 단위로 한다. 1GB 미만은 "340MB", 이상은 "1.4GB"다. 크기 제한 2GB가 2,147,483,648바이트라 표시도 같은 단위로 맞춘다. 십진 단위로 보여주면 제한에 걸린 파일의 크기가 2GB보다 작게 표시되어 거절 이유가 말이 안 되어 보인다.

### 변환 파이프라인

변환은 모델 준비와 음성 추출, 변환 세 단계를 차례로 지난다. 화면에는 세 단계가 목록으로 보이고 지금 단계의 진행률이 그 아래에 붙는다.

**모델 준비.** 브라우저 캐시에 음성 인식 모델이 있는지 먼저 확인한다. 없으면 약 600MB를 내려받고 내려받은 용량을 "312MB / 600MB" 형식으로 보여준다. 받은 모델은 브라우저 캐시에 저장한다. 캐시에 모델이 있으면 다운로드 없이 캐시에서 읽어 이 단계가 짧게 끝난다.

**음성 추출.** 영상 파일의 오디오 트랙을 브라우저 내장 디코더로 해독하고 음성 인식이 받는 형식인 16kHz 모노 PCM으로 바꾼다. 오디오 트랙이 없거나 해독에 실패하면 실패 안내 화면으로 간다.

**변환.** 추출한 음성을 한국어 텍스트로 바꾼다. 진행률은 전체 음성 길이 가운데 처리를 마친 시간의 백분율로 보여준다. 결과는 구간 단위로 나오고 구간마다 시작 시각과 끝 시각이 붙는다.

세 단계가 모두 끝나면 결과 화면으로 간다. 중단 버튼은 없다. 모든 처리가 기기 안이라 새로고침으로 처음부터 다시 하면 되고 잃는 것은 시간뿐이다.

### 결과

**문장과 시작 시각.** 문장 단위는 음성 인식이 나눈 구간을 그대로 쓴다. 화면의 문장 목록과 txt, 전체 복사에서 시작 시각의 표기는 1시간 미만이면 `mm:ss`, 1시간 이상이면 `h:mm:ss`로 통일한다.

기준은 구간 하나의 시각이 아니라 전체 길이다. 구간마다 판정하면 2시간 영상에서 3초 구간이 `00:03`, 1시간 5분 구간이 `1:05:03`으로 나와 한 목록 안에서 표기가 섞인다.

전체 길이는 추출한 음성의 길이로 잰다. 영상 자체의 길이와 거의 같지만 오디오 트랙이 영상보다 짧으면 다를 수 있다. 목록과 txt, 전체 복사가 모두 같은 값을 쓰므로 셋끼리 어긋나지는 않는다.

**문장 클릭.** 문장 행을 클릭하면 플레이어가 그 문장의 시작 시각으로 이동해 재생한다. 일시정지 상태였어도 재생을 시작한다. 재생 중에는 현재 재생 시각이 시작 시각 이상이고 다음 문장의 시작 시각 미만인 문장을 재생 중인 문장으로 판정해 목록에서 강조한다.

**전체 복사.** 아래 txt 형식과 같은 내용을 클립보드에 복사한다. 성공하면 "복사했습니다", 실패하면 "복사하지 못했습니다"를 2초 동안 보여준다.

**문장이 하나도 없는 결과.** 오디오는 멀쩡한데 말이 없는 영상이면 음성 인식이 구간을 내지 않는다. 이것은 실패가 아니라 정상으로 끝난 변환이라 결과 화면으로 간다. 문장 목록 자리에 "이 영상에서 문장을 찾지 못했습니다. 음성이 없거나 너무 작을 수 있습니다"를 보여주고 전체 복사와 내려받기 버튼 넷을 비활성으로 둔다. "새 영상 변환"은 살려 둔다.

버튼을 살려 두면 눌러서 빈 파일을 받게 되고, 사용자는 무엇이 잘못됐는지 모른 채 파일이 깨진 것으로 읽는다. 오디오 길이가 0인 `EMPTY_AUDIO`와는 다른 경우다. 그쪽은 음성 추출 단계에서 실패로 끝난다.

**재생 중 판정의 경계.** 마지막 문장에는 다음 문장이 없으므로 위쪽 경계를 두지 않는다. 영상 끝까지 마지막 문장이 재생 중으로 남는다. 판정이 이 문장의 끝 시각이 아니라 다음 문장의 시작 시각을 쓰기 때문이다. 문장 사이가 비어 있어도 앞 문장 강조가 남는 것과 같은 규칙이다.

플레이어를 시작 시각으로 옮기면 그 자리에 정확히 서지 않고 백만분의 일 초쯤 앞에 선다. 그대로 두면 방금 누른 문장이 아직 시작하지 않은 것이 되어 바로 위 문장이 강조된다. 시각 표기가 밀리초까지이므로 그보다 작은 차이는 같은 자리로 본다.

**내려받기.** 파일 이름은 원본 영상 이름에서 확장자만 바꾼다. `meeting.mp4`를 변환하면 `meeting.txt`와 `meeting.srt`, `meeting.vtt`가 된다. 인코딩은 셋 다 UTF-8이다.

txt는 한 문장이 한 줄이고 줄 앞에 시작 시각을 대괄호로 붙인다.

```
[00:03] 안녕하세요, 오늘 회의를 시작하겠습니다.
[00:07] 지난주에 이야기한 일정부터 확인하겠습니다.
```

srt는 자막 번호와 시간 범위, 문장을 빈 줄로 구분해 쌓는다. 번호는 1부터 차례로 붙이고 시각은 시, 분, 초를 콜론으로 잇고 밀리초를 쉼표로 구분한다. 끝 시각은 음성 인식이 준 구간의 끝 시각이다.

```
1
00:00:03,200 --> 00:00:07,500
안녕하세요, 오늘 회의를 시작하겠습니다.

2
00:00:07,500 --> 00:00:12,000
지난주에 이야기한 일정부터 확인하겠습니다.
```

vtt는 첫 줄에 `WEBVTT`를 쓰고 빈 줄 뒤에 시간 범위와 문장을 쌓는다. 시각 표기는 srt와 같되 밀리초를 마침표로 구분한다.

```
WEBVTT

00:00:03.200 --> 00:00:07.500
안녕하세요, 오늘 회의를 시작하겠습니다.

00:00:07.500 --> 00:00:12.000
지난주에 이야기한 일정부터 확인하겠습니다.
```

### 실패 처리

**비지원 브라우저.** 접속하면 먼저 WebGPU를 쓸 수 있는지(`navigator.gpu` 존재 여부) 확인한다. 없으면 업로드 화면 대신 비지원 브라우저 안내를 보여준다. 데스크톱 Chrome이나 Edge 최신 버전으로 열어 달라는 내용과 영상을 서버에 올리지 않고 브라우저 안에서만 처리하는 방식이라 이 브라우저들이 필요하다는 이유를 함께 적는다.

**음성 추출 실패.** 오디오 트랙이 없거나 내장 디코더가 해독하지 못하는 파일이면 실패 안내 화면으로 간다. 문구는 "이 파일에서 음성을 찾지 못했습니다"처럼 무엇이 안 됐는지 밝힌다. "다른 파일 선택" 버튼으로 업로드 화면에 돌아간다.

**변환 진행 중 그 밖의 실패.** 모델 다운로드가 네트워크 문제로 끊기거나 음성 인식 중 오류가 나도 같은 실패 안내 화면으로 간다. 문구에 어느 단계가 실패했는지 적는다.

실패 사유마다 보여줄 문구를 정한다. 코드는 파이프라인이 던지는 실패 코드이고 화면은 이 표에서 문구를 고른다. 예외 객체의 `message`는 개발자용이라 화면에 그대로 내보내지 않는다.

| 단계       | 코드            | 문구                                                                                                               |
| ---------- | --------------- | ------------------------------------------------------------------------------------------------------------------ |
| 음성 추출  | `FILE_READ`     | 파일을 읽지 못했습니다. 파일이 옮겨지거나 지워졌을 수 있습니다                                                     |
| 음성 추출  | `DECODE`        | 이 파일에서 음성을 찾지 못했습니다                                                                                 |
| 음성 추출  | `EMPTY_AUDIO`   | 이 파일에서 음성을 찾지 못했습니다                                                                                 |
| 음성 추출  | `RESAMPLE`      | 음성을 추출하지 못했습니다. 영상이 길어 메모리가 모자랐을 수 있습니다                                              |
| 모델 준비  | `MODEL_PREPARE` | 음성 인식 모델을 준비하지 못했습니다. 네트워크 연결을 확인하고 브라우저를 최신 버전으로 올린 뒤 다시 시도해 주세요 |
| 변환       | `TRANSCRIBE`    | 음성을 텍스트로 바꾸는 중 실패했습니다                                                                             |
| 알 수 없음 | `UNKNOWN`       | 변환 중 알 수 없는 문제가 생겼습니다                                                                               |

`UNKNOWN`은 어느 단계에서 났는지 가려낼 수 없는 예외를 받는다. 이 코드가 없으면 정체 불명 예외를 다른 코드에 떨어뜨려야 하고, 모델 단계에서 터진 것에 변환 실패 문구가 나가 화면이 사실과 다른 말을 한다.

`MODEL_PREPARE`는 모델 파일을 내려받지 못한 경우와 WebGPU 세션을 만들지 못한 경우를 함께 받는다. 라이브러리가 다운로드와 세션 생성을 한 호출로 처리해 어느 쪽에서 터졌는지 가려낼 수 없다. 그래서 문구가 네트워크만 짚지 않고 브라우저 버전도 함께 짚는다. 네트워크만 짚으면 그래픽 드라이버 문제인 사용자가 연결을 확인하다 시간을 버린다.

`DECODE`와 `EMPTY_AUDIO`가 같은 문구인 이유는 브라우저가 둘을 구분해 주지 않기 때문이다. 오디오 트랙이 없는 파일과 코덱을 해독하지 못하는 파일이 모두 같은 `EncodingError`로 온다. 사용자에게는 어느 쪽이든 이 파일에서 음성을 찾지 못한 것이 사실이다.

## 기술 결정 기록

아이디에이션에서 확정한 결정과 이유를 남긴다. 결정을 바꾸면 이 절을 고친다.

### 음성 인식: transformers.js로 Whisper를 브라우저에서 실행

모델은 whisper-large-v3-turbo 양자화 버전(약 600MB)을 쓰고 WebGPU로 가속한다. 한국어 인식 품질이 제품의 존재 이유라서 작은 모델 대신 큰 모델을 골랐다.

### 오디오 추출: 브라우저 내장 디코더만 사용

OfflineAudioContext로 영상 파일의 오디오를 디코딩한다. 의존성이 없고 Chrome에서 mp4와 mov의 AAC 오디오를 디코딩할 수 있다. ffmpeg.wasm은 지금 붙이지 않는다. 내장 디코더로 열지 못하는 파일이 실제로 나오면 그때 붙일 대비책으로만 기록해 둔다.

### 모델 캐시: 브라우저 캐시에 저장

내려받은 모델을 브라우저 캐시에 저장해 두 번째 방문부터는 다운로드 없이 바로 시작한다. PRD 성공 기준이 요구하는 동작이다.

### 지원 브라우저: 데스크톱 Chrome과 Edge 최신 버전만

변환 속도가 WebGPU에 달려 있어 WebGPU가 되는 이 둘만 지원한다. WebGPU 없이 도는 폴백 경로는 만들지 않는다.

### 배포: GitHub Pages 정적 배포

서버가 없는 정적 사이트라 GitHub Pages로 충분하다. GitHub Pages는 응답 헤더를 마음대로 설정할 수 없지만 오디오 추출에 내장 디코더를 쓰는 방식은 COOP와 COEP 헤더가 필요 없어서 문제가 되지 않는다.

저장소 이름이 주소에 붙는 프로젝트 페이지라 `base`를 `/vidscript/`로 잡는다. 이 값은 산출물의 절대 경로 셋을 함께 바꾼다. `index.html`의 favicon과 스크립트, CSS의 `@font-face` url, 워커 안의 wasm 주소다. 셋 다 소스에서는 호스트 루트를 가리키는 문자열이라 `base`를 넣은 뒤 산출물에서 직접 확인한다. 폰트가 404가 나면 폴백 폰트로 그려져 화면이 그럴듯하게 망가지고, wasm이 404가 나면 모델을 다 받은 뒤 세션 생성에서 터진다.

개발 서버와 미리보기도 같은 경로 아래에서 돈다. 임시 개발 페이지 주소가 `/vidscript/dev.html`이 된다.

### 스택: React 19와 Vite 8, TypeScript 6

Vite 8은 번들러로 Rolldown, CSS 처리로 Lightning CSS를 내장한다. 둘을 따로 붙이지 않는다.

TypeScript는 6에 남는다. 7이 네이티브 컴파일러로 나와 타입 검사가 빨라지지만 `typescript-eslint`의 peer가 `typescript <6.1.0`이라 7로 올리면 지금의 ESLint 구성이 깨진다. 린터를 Rust 기반으로 바꾸면 함께 올릴 수 있고, 그때 다시 본다.

### 스타일링: Tailwind CSS v4

v4의 `@theme` 블록은 `--color-brand` 같은 CSS 커스텀 프로퍼티와 유틸리티 클래스를 함께 만들어 낸다. `DESIGN.md`의 색 표 이름을 그대로 옮기면 문서의 이름과 코드의 이름이 일치해 검증에서 기계적으로 대조할 수 있다. 컴포넌트에 hex 값을 직접 쓰지 않는다.

### React Compiler: Babel 경로로 적용

메모화를 손으로 달지 않는다. 결과 화면의 문장 목록은 재생 위치가 바뀔 때마다 수백 행을 다시 그릴 수 있어 이득이 실제로 난다. `@vitejs/plugin-react`가 Rust 경로와 Babel 경로 둘을 제공하는데 Rust 경로에 experimental 표시가 붙어 있어 Babel 경로를 쓴다.

### 테스트: Vitest, node 환경만

`OfflineAudioContext`와 WebGPU는 node에도 jsdom에도 없어서 오디오 추출과 음성 인식은 자동 테스트로 덮지 못한다. 브라우저 모드를 붙이면 Playwright가 함께 배포하는 Chromium이 H.264와 AAC 디코더가 빠진 빌드라서, 멀쩡한 mp4에서도 디코딩 실패가 나는 함정을 안게 된다.

대신 실제로 버그가 나는 자리는 대부분 순수 함수다. 시각 표기가 세 형식마다 다르고, 업로드 검증은 순서가 규칙이며, txt와 srt, vtt 생성기는 입력과 출력이 문자열이다. 이쪽을 node에서 덮고 브라우저 API에 묶인 부분은 임시 개발 페이지에서 손으로 확인한다.
