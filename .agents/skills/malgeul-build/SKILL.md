# malgeul-build

말글의 구현 작업을 에이전트 팀으로 진행하는 오케스트레이터다. 리더(메인 세션)가 팀을 꾸리고 조율하며, 구현은 팀원이 한다. 무엇을 만드는지의 정본은 `docs/`에 있고 만드는 순서는 `docs/product/ROADMAP.md`가 정한다.

## 실행 모드: 에이전트 팀

팀원은 Agent 도구로 name과 subagent_type, model을 지정해 띄운다. 모든 호출에 `model: "opus"`를 명시한다. 팀과 공유 작업 목록 도구(TeamCreate, TaskCreate)가 있는 환경에서는 그것을 쓰고, 없으면 Agent와 SendMessage, 파일 기반 산출물로 같은 구조를 만든다.

## 에이전트 구성

| 팀원         | subagent_type | 역할                                    | 전담 스킬      |
| ------------ | ------------- | --------------------------------------- | -------------- |
| pipeline-dev | pipeline-dev  | 오디오 추출, 음성 인식, 내보내기 생성기 | stt-pipeline   |
| ui-dev       | ui-dev        | 화면과 상태 머신, 디자인 토큰           | ui-conventions |
| qa-inspector | qa-inspector  | 게이트와 경계면 교차 비교, ROADMAP 갱신 | qa-gates       |

마일스톤마다 필요한 팀원만 띄운다. 오디오 추출 검증과 음성 인식 파이프라인은 pipeline-dev와 qa-inspector, 업로드와 진행 UI는 ui-dev와 qa-inspector, 결과 화면과 내보내기는 셋 모두가 필요하다.

## 워크플로우

### Phase 0: 컨텍스트 확인

이 프로젝트에서 진행 상태의 정본은 별도 작업 폴더가 아니라 ROADMAP 체크리스트와 git이다.

1. `docs/product/ROADMAP.md`의 체크 상태로 어디까지 왔는지 읽는다
2. `git log --oneline -10`과 `git status`로 실제 코드 상태를 대조한다. 체크는 안 됐는데 코드가 있으면 검증되지 않은 코드이니 qa-inspector 검증부터 시작한다
3. 실행 모드를 정한다
   - 사용자가 특정 부분 수정이나 버그를 말하면 부분 재실행이다. 해당 영역의 구현자와 qa-inspector만 띄운다
   - 사용자가 마일스톤이나 기능을 지정하면 그것을, 지정하지 않으면 ROADMAP의 다음 미완 마일스톤을 대상으로 잡는다

### Phase 1: 계획

1. 대상 마일스톤의 체크리스트 항목을 작업 단위로 나누고 팀원별로 배정한다
2. 병렬 가능성을 판단한다. 서로 다른 파일을 만지는 작업만 병렬로 하고, 같은 파일을 만질 작업은 순서를 정한다
3. 브랜치를 확인한다. main에서는 `feature/{이름}` 브랜치를 먼저 딴다. 커밋은 사용자가 요청할 때만 한다
4. 계획(대상, 작업 배정, 순서)을 사용자에게 요약 보고하고 시작한다

### Phase 2: 경계면 계약

pipeline-dev와 ui-dev가 함께 일하는 마일스톤에서는 구현 전에 공개 타입(변환 구간, 진행 이벤트)을 먼저 합의시킨다. pipeline-dev가 타입 파일 초안을 만들고 ui-dev가 화면에 필요한 shape을 검토해 확정한다. 커밋된 타입 파일이 계약이고, 바꿀 때는 양쪽에 알린다. 이 단계를 건너뛰면 두 사람이 각자 올바른 코드를 만들고 만나는 지점에서 어긋난다.

### Phase 3: 구현

팀원들이 배정된 작업을 수행한다. 통신 규칙은 각 에이전트 정의의 팀 통신 프로토콜을 따른다.

리더는 진행을 지켜보다 다음에 개입한다.

- 팀원이 정본 문서와 코드의 충돌을 보고하면 문서가 이기는 것이 기본이되, 문서가 틀린 것으로 판단되면 사용자에게 확인받아 문서를 고친다
- 팀원이 같은 문제로 3회 막히면 접근을 바꾸거나 작업을 재배정한다

### Phase 4: 점진 QA

모듈 하나가 끝날 때마다 qa-inspector에게 그 모듈의 검증을 시킨다. 전체 완성까지 검증을 미루면 경계면 불일치가 후속 모듈로 전파된다. 발견된 실패는 qa-inspector가 해당 구현자에게 직접 수정 요청을 보내고, 수정 후 재검증까지가 한 사이클이다.

### Phase 5: 완료

1. qa-inspector가 게이트 전체(type:check, build, lint, format:check)를 마지막으로 한 번 돌린다
2. 증거가 있는 항목만 ROADMAP 체크리스트에 체크한다. 수동 확인이 필요한 항목(소리가 들리는지, 30분 영상 메모리)은 사용자에게 확인 방법을 안내하고 남긴다
3. 사용자에게 결과를 보고한다. 만든 것과 확인한 것, 남은 것을 구분한다
4. 피드백을 요청한다. 결과물이나 팀 구성, 워크플로우에 고칠 점이 있는지 묻고, 있으면 해당 에이전트 정의나 스킬을 수정하고 AGENTS.md 하네스 변경 이력에 기록한다

## 데이터 전달

- 산출물의 정본은 코드와 docs/ 문서다. 별도 작업 폴더를 만들지 않는다. 저장소를 어지럽히고 정본과 사본이 갈라지기 때문이다
- 팀원 간 실시간 조율은 SendMessage로 한다
- 경계면 계약은 커밋된 타입 파일로 한다
- QA 리포트는 qa-inspector가 리더에게 메시지로 보내고, 리더가 사용자 보고에 요약한다

## 에러 핸들링

| 상황                                 | 대응                                                                                        |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| 팀원 하나가 실패하거나 멈춤          | 상태를 확인하고 1회 재시작. 재실패하면 작업을 다른 팀원이나 리더가 인수하고 보고에 명시한다 |
| 게이트가 3회 연속 같은 원인으로 실패 | 변경을 되돌리고 설계로 돌아간다. 4회째 같은 방법을 시도하지 않는다                          |
| 정본 문서끼리 충돌                   | 삭제하지 않고 양쪽을 사용자에게 보여 결정을 받는다                                          |
| 팀원이 범위 밖 파일을 수정           | 되돌리고 해당 작업만 다시 시킨다                                                            |

## 테스트 시나리오

### 정상 흐름: 오디오 추출 검증 마일스톤

1. 사용자가 "마일스톤 진행해줘"라고 요청한다
2. Phase 0에서 ROADMAP을 읽어 첫 마일스톤이 미완임을 확인한다
3. Phase 1에서 체크리스트 다섯 항목을 pipeline-dev에게 배정하고 feature/audio-extraction 브랜치를 확인한다
4. Phase 3에서 pipeline-dev가 디코딩과 리샘플링, 임시 개발 페이지를 구현한다
5. Phase 4에서 qa-inspector가 게이트와 실패 파일 처리를 검증한다
6. Phase 5에서 증거 있는 항목을 체크하고, 소리가 들리는지는 사용자 확인으로 남긴다

### 에러 흐름: 경계면 불일치 발견

1. 결과 화면 마일스톤에서 ui-dev가 진행 이벤트를 백분율 단일 필드로 소비하는 코드를 만든다
2. qa-inspector가 교차 비교에서 모델 다운로드 용량 표시가 불가능함을 발견한다
3. qa-inspector가 pipeline-dev와 ui-dev 모두에게 알리고, 두 사람이 진행 이벤트 타입을 용량과 백분율을 구분하는 형태로 다시 합의한다
4. 수정 후 재검증을 통과하면 진행한다
