# qa-gates

vidscript 구현이 정본 문서와 일치하는지 검증하는 절차다. 핵심은 존재 확인이 아니라 교차 비교다. "생성기가 있는가"가 아니라 "생성기의 출력이 SPEC의 예시와 일치하는가"를 확인한다.

## 게이트

빠른 실패 순서로 돌린다.

```bash
pnpm type:check
pnpm build
pnpm lint
pnpm format:check
```

하나라도 실패하면 완료가 아니다. 게이트를 통과시키려고 lint 규칙을 끄거나 타입을 any로 눌러 놓는 것은 게이트를 통과한 것이 아니라 치운 것이다. 발견하면 실패로 보고한다.

## 경계면 교차 비교

이 프로젝트의 경계면 목록이다. 각 항목은 왼쪽(정본이나 생산자)과 오른쪽(코드나 소비자)을 동시에 열어 비교한다. 해당 모듈이 만들어진 뒤에만 검증할 수 있으므로, 검증 시점에 존재하는 것만 대조하고 나머지는 미검증으로 표시한다.

| 왼쪽                             | 오른쪽                | 방법                                                                                                       |
| -------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------- |
| SPEC 거절 문구 표                | 코드의 문구 문자열    | 표의 다섯 문구를 grep으로 찾아 글자 단위 일치 확인                                                         |
| SPEC의 txt, srt, vtt 출력 예시   | 생성기 실제 출력      | 예시와 같은 구간 데이터를 만들어 생성기에 넣고 출력을 문자 단위 비교. 스크립트로 실행한다                  |
| SPEC 업로드 검사 순서            | 검증 코드의 검사 순서 | 개수, 확장자, 크기, 길이 순서와 첫 실패만 보여주는 동작 확인                                               |
| 파이프라인 공개 타입             | UI의 소비 지점        | 타입 정의와 사용처를 같이 읽고 캐스팅(as)으로 우회한 곳이 없는지 확인                                      |
| 진행 이벤트의 용량과 백분율 구분 | 진행 화면 표시        | 모델 다운로드는 용량, 나머지 단계는 백분율로 갈리는지 확인                                                 |
| DESIGN 색 표의 이름과 값         | CSS 커스텀 프로퍼티   | 표의 열 개 토큰이 같은 이름과 hex 값으로 존재하는지, 컴포넌트에 hex 직접 사용이 없는지 grep                |
| DESIGN-SPEC 상태 전이 표         | 상태 머신 코드        | 표의 전이가 모두 코드에 있고(죽은 전이 없음) 코드의 전이가 모두 표에 있는지(무단 전이 없음)                |
| 외부 요청 목록                   | 실제 네트워크 요청    | 허용된 외부 요청은 Hugging Face 모델 다운로드뿐이다. 폰트 CDN, 분석 스크립트, 영상 전송은 발견 즉시 실패다 |

## 검증 스크립트

눈으로 훑지 말고 실행해 비교한다. 생성기 검증은 이런 식이다.

```bash
pnpm exec tsx scripts/qa/verify-exporters.ts
```

스크립트가 없으면 만들어 `scripts/qa/`에 둔다. 같은 검증을 반복하게 되므로 일회용으로 버리지 않는다.

## ROADMAP 체크리스트 갱신

`docs/product/ROADMAP.md`의 체크박스는 증거가 있을 때만 체크한다. 증거는 게이트 출력이나 실행한 확인 방법이다. "구현했으니 체크"는 증거가 아니다. 체크하면서 리더 보고에 무엇을 어떻게 확인했는지 한 줄씩 남긴다.

수동 확인이 필요한 항목(추출한 음성이 들리는지, 30분 영상의 메모리)은 에이전트가 대신 체크하지 않는다. 사용자에게 확인 방법을 안내하고 미검증으로 남긴다.

## 리포트 형식

```
## 검증 리포트: {모듈}
- 게이트: type:check 통과, build 통과, lint 통과, format 통과
- 통과: {항목과 확인 방법}
- 실패: {항목, 파일:라인, 수정 방법}
- 미검증: {항목과 이유. 사용자 수동 확인 필요 항목 포함}
```

실패는 발견 즉시 해당 구현자에게 보내고 리포트에도 남긴다. 경계면 이슈는 양쪽 구현자 모두에게 알린다.
